## はじめに

ユーザが入力した値によって「遷移する画面」と「ユーザが選択可能な項目」が変わるフォームを実装したことがありました。例えばサンドウィッチを作るフォームでは、以下のように入力値に応じて画面や選択肢が変わります(詳しくはデモサイトで触れます)。

- ベジタリアンを選ぶと肉と魚を含む具材選択ページに遷移しない(遷移する画面が変わる)
- エビNGを選ぶと、サイドメニューでガーリックシュリンプを選べない(ユーザの選択可能な項目が変わる)

こういったユーザ入力によって変わる状態は複雑で管理が大変です。そこで、ステートマシンを使って、入力値をトリガーに変化する「遷移する画面」と「ユーザが選択可能な項目」をすべて一意の状態として管理できれば、処理が宣言的に書けるのではないかと考えました。また、ステートマシンから、見やすい状態遷移図を生成できるとも考えました。しかし、タイトルにもあるように、ステートマシンでの管理はうまく行きませんでした。

本記事では、デモサイトを見ながらフォームの実装にステートマシンを使おうとして失敗したことと、なぜ失敗したかを書きます。最後に、最終的に採用した「遷移する画面」と「ユーザが選択可能な項目」の管理方法を紹介します。

## ステートマシンを使って実装した結果

### 失敗例1: 素直に「1ページ = 1状態」としてxstateでモデリング

1ページを1状態として扱うと、入力の組み合わせ分だけ状態が必要になり、組み合わせ爆発が起きました。ページ数が「入力の組み合わせ数」と等しくなってしまうためです。

例えば、エビNGを選択した場合は `mainMeal`ページに「エビ」が入らなくなるので、通常の具材選択をする`mainMeal`ページとエビを除いた`mainMealNoShrimp`ページを分ける必要があります。
加えて、ステートマシンでは直前の状態(xstateのstate)からしか次のページの状態を決められません。そのため、後半のサイドメニューを選ぶ`sideMenu`ページに行くまで、ユーザがエビNGを選択したという情報をページに持たせて運ぶ必要があります。結果、エビNGのユーザがたどる遷移は `mainMealNoShrimp -> vegetableNoShrimp -> sourceNoShrimp -> hotNoShrimp -> sideMenuNoShrimp` のようになってしまいます。

結果的に、ステートマシンで「遷移する画面」と「ユーザが選択可能な項目」を管理すると組み合わせ爆発を起こすため失敗しました。

### 失敗例2: nextとbackの処理にguardが必要になる

失敗例1が複雑化したのは「遷移する画面」と「ユーザが選択可能な項目」を同時に管理しようとしたからでした。失敗例2では後者を諦め、「遷移する画面」のみをステートマシンで管理しました。しかしこれも失敗しました。理由は2つあります。

第一に、案件にあった既存storeと併用したためです。xstateには[context](https://stately.ai/docs/context)というデータを保存する機能がありますが、既存のフォームstoreと併用したところ、ステートマシンから結局storeを呼ばなければならなくなりました。これだと`stateMachine.ts`が唯一の情報源ではなくなるのでデータが二重管理になります。

第二に、分岐ロジックが二重化したことです。これは失敗例1と同じ構造ですが、次のページに行くための情報を前のページからしか決められないので、`next`と`back`のそれぞれに同じguardを書く必要がありました。<!-- textlint-disable ja-technical-writing/no-doubled-joshi -->
例えば「ベジタリアンを選んだユーザは`choiceUser`から`vegetable`へ直接進む」ロジックと、「戻るときに`mainMeal`を飛ばす」ロジックは意味的に同じですが、`next`側と`back`側で二重に書くことになります。

## 解決策: 遷移する画面と選択可能な項目を入力データから導出する

ページ構成をステートマシンの一意の状態として持つのではなく、入力データから導出する形に変えました。
入力データによって変わるのは「遷移する画面」と「ユーザが選択可能な項目」の2つなので、それぞれを別のcomposableで導出しています。

### `useInputStep.ts`: 遷移する画面の導出

フォームの値をもとに、ユーザが到達可能なページを追加していきます。computedのため、フォームの値が変わると到達可能なページが再計算されます。

```ts
// 制約: ベジタリアンは肉・魚を食べないので具材ページを出さない
if (data.choiceUser !== "vegetarian") {
  steps.push("mainMeal");
}
```

### `useFilteredOptions.ts`: ユーザが選択可能な項目の導出

フォームの選択状態からfilterされた選択可能項目を返すcomposablesを作成しました。エビNGのユーザの場合に`mainMeal`ページでエビを選択しないロジックは以下のようになります。

```ts
const filteredMainMeal = computed(() =>
  formData.value.choiceUser === "noShrimp"
    ? mainMealValues.filter((value) => value !== "shrimp")
    : mainMealValues
);
```

## まとめ

「データから導出できる値をステートマシンの一意の状態として管理すべきでない」ということがわかりました。
今後ステートマシンを使う場合は、決済フロー、認証フローなどの状態が有限で列挙できる場合に使用すべきだと考えました。
